# 核心组件

> 本文逐一说明每个组件**是什么、负责什么、边界在哪**。
> 配置与使用方法见 [配置手册](configuration.md)；结构与依赖见 [系统架构](architecture.md)。

状态标记：✅ 可用 · 🚧 建设中

## 1. FinDataHub（接入层）✅

**定位**：唯一的源访问面。所有数据源调用都经过它，平台其余部分不接触供应商 SDK。

**职责**

- **适配**：按资产类型与接口能力适配各数据源（Tushare / Wind / iFinD / AkShare / Fuyao / BaoStock）；
- **归一**：统一代码模型（`symbol.VENUE`，如 `600000.SH`、`000001.OF`）与统一输出 schema；
- **Router（跨源合成）**：以请求的 `source` 为主源——缺字段时从补充源 coalesce 补全、
  缺复权能力时以「原始价 + 因子」合成、主源失败时按配置回退，结果携带溯源；
- **限流**：每源独立的令牌桶（QPS），等待超时抛出明确错误；
- **缓存**：进程内 TTL + LRU + 字节预算，`force=True` 跳过缓存；
- **计量**：按源统计调用次数与估算成本、预算告警，支持回调导出做跨进程汇总。

**边界**：只做归一化与合成，**不落数据**；不决定数据存到哪张表；不做业务口径判断。

**关键概念**：`source` 显式且语义不可变（补全与回退不改变主源标注）；按需触发补充调用
（成本最小化）；结果 `df.attrs` 携带 `source / cached / fetched_at` 等元信息。

**代码**：`src/fin_data_hub/`（`facade.py` 门面、`routing.py` 路由、`sources/` 适配器、
`ratelimit.py`、`cache.py`、`usage.py`）

### 各源支持范围

逐源状态、已知问题与对账结论见 [数据源](data-sources.md)；下表为能力速查。

| 能力 | Tushare | AkShare | Wind | iFinD | Fuyao | BaoStock |
|---|---|---|---|---|---|---|
| 日线行情 | ✅（含 qfq/hfq） | ✅ 股票 / ETF / LOF / 指数 | ⚠️ 单代码逐次 | ⚠️ 仅指数 | ✅ 单标的（长窗口分块） | ✅ SH/SZ |
| 快照 | — | — | ✅ 单次批量 | — | ✅ 批量 | — |
| 场外基金净值 | ✅ | ✅ | — | ✅ 多基金合并 | — | — |
| 参考数据 | ✅ | — | — | — | ✅ 列表类 | — |
| 标的 / 指数成分 / 财务 / 事件 | ✅ | — | — | — | — | — |
| 交易日历 | ✅ | ✅ | — | — | ✅（一年窗口） | — |
| 宏观 / 债券等特色接口 | — | — | ✅ | ✅ | — | — |

限制说明：

- **Wind**：日线不接受 `period` 参数；K 线为单代码接口，多代码由库逐次调用；
- **iFinD**：K 线目前仅支持指数；其自然语言类接口普遍支持多标的 / 多指标聚合，
  由库合并为单次调用，单次请求标的数有安全上限；
- **AkShare**：无参考数据接口、不支持快照；各接口为单标的形式，批量请求由库自动拆分；
- **BaoStock**：仅支持沪深两市（`sh.` / `sz.` 前缀，含指数）；原生复权不列入可信源；
  连接断开自动重新登录；
- **Tushare**：行情按资产类型路由（股票 / ETF-LOF / 指数使用不同接口）；
  复权只对个股类标的（股票 / ETF / LOF）有意义——指数不存在价格复权概念，
  请求指数复权会被显式拒绝而非静默忽略；
- **Fuyao**：快照能力主力来源（Wind 亦具备，暂不配置回退）；原生复权序列不可用，
  请求复权时由 Router 组合「原始价 + 因子」合成（需配置因子源）。

## 2. Dictionary（数据契约）✅

**定位**：机器可读的数据契约，是"我们有哪些数据、以什么口径存在"的唯一事实来源。

**职责**

- 数据集（DataPanel）登记：字段 / 类型 / 单位 / PIT 角色 / 主键 / 粒度 / SLA / 覆盖率；
- 质量规则与血缘（上游数据集与转换）；
- 源映射（每个 canonical 字段来自哪个源字段）与采集入口声明；
- 派生登记（算法标识、实现路径、输入）；
- **Schema First**：数据库 DDL、迁移基线、读模型与生成式文档由契约派生或强校验。

**边界**：定义"数据是什么"，不做数据搬运；不承载运行状态（运行、质量结果在控制面）。

**关键概念**：字段兼容不等于语义兼容；契约变更走 CI 校验与版本评审。

**代码**：`src/fin_data_platform/dictionary/`（含 `ref/` 参照数据与各数据域目录）

## 3. Entity Registry（实体身份）✅

**定位**：回答"数据说的是谁"——实体身份、关系与外部标识的唯一权威。

### 为什么需要这一层

把代码当作身份，是多源数据里最容易犯、也最昂贵的错误。四个现实问题决定了
必须有独立的一层来管理身份：

1. **一串代码不是一个人**。代码会变更（更名、市场迁移）、会被复用（退市后原代码
   交给新标的）；同一实体在不同源有不同写法（带后缀 / 裸代码 / 源内部编号）。
   用代码做跨源主键，历史一断，所有拼接都错。
2. **一家公司不等于一只证券**。同一家发行主体可能同时拥有 A 股、B 股、H 股、
   可转债等多只证券，分散在不同市场与类型；而财务、股东、公司事件说的是**公司**，
   行情、成分、复权说的是**证券**。若不区分，财务数据就会挂到某一只股票上，
   或跨源永远对不上。
3. **代码之外还有关系信息**。母子公司、控制关系、发行关系构成图结构，
   查询与治理都需要词表约束，而不是散落在各数据集的自由文本字段里。
4. **跨源对齐需要稳定外部标识**。ISIN / LEI / 统一社会信用代码等是跨源、跨市场
   对齐的锚点；Ticker 会变，外部标识相对稳定。

### issuer 与 listing：为什么要分开

| 概念 | 含义 | 挂载的数据 |
|---|---|---|
| **issuer（发行主体）** | 法律主体：工商注册的公司 / 机构 | 财务报表、股东、公司事件、主体属性（存续状态等） |
| **listing（上市实体）** | 证券市场中的交易标的：股票、ETF、基金、指数、债券等 | 行情、复权因子、指数成分、净值 |
| 关系（如 `issued_by`） | listing → issuer 的发行关系 | 连接两侧数据的桥梁 |

分开的直接收益：

- **口径正确**：公司级数据只挂 issuer 一次，不因多个证券而重复；
  行情级数据只挂 listing，不与公司主体混淆；
- **可扩展**：同一主体新增上市地 / 新证券时，只增加 listing 与关系，历史不受影响；
- **可追溯**：分红、股本这类"两侧都有"的数据，经关系落位到正确的一侧，
  跨源核对时有共同锚点。

非发行类的实体（指数、篮子等）同样登记为实体，只是不走 issuer 关系；
「谁发行、谁交易、谁编制」由类型与关系共同表达。

### 其余设计要点

- **稳定主键**：实体一经登记，拥有不随代码变化的稳定标识，所有数据集引用它；
- **代码履历**：代码变更与复用写入履历，旧代码仍可解析回同一实体；
- **关系是词表驱动的**：关系类型必须先登记，单向存储、双向查询由词表元数据生成
  （零硬编码），新增关系类型不需要改查询逻辑；
- **外部标识**：登记 ISIN / FIGI / CUSIP / SEDOL / LEI / USCC 等跨源锚点（不含 Ticker——
  Ticker 是代码，属履历）；
- **身份与状态分离**：交易状态（上市 / 停牌 / 退市）是数据、不是身份，
  由数据集承载；某历史时点的可交易集合（PIT 宇宙）由数据集推导；
- **属性保留历史**：名称、类型等属性按 SCD2 保存区间，任意时点可还原当时值。

**边界**：不含交易状态（属数据集）；不含数据目录（属字典）；不维护源映射；
不含算法登记（属派生引擎）。

**代码**：`src/fin_data_platform/registry/`（身份、代码履历、关系、外部标识、PIT Universe）

## 4. Storage（PIT 存储）✅

**定位**：把契约与时间语义落到数据库，并保证幂等与可回放。

**职责**

- 按字典生成 schema（表、分区、压缩、读模型）；
- 幂等写入：物理键判重，重跑不产生新版本；
- as-of 与最新态读取、实体读模型；
- 版本化迁移（升级 / 回滚 / 版本校验）。

**边界**：不定义口径（字典定义）；不做源适配（接入层负责）；消费侧不直读物理表。

**关键概念**：Raw → Canonical → Read Model；事件时间与知识时间分离；
hypertable 分区与压缩；SCD2 区间；读模型语义版本。

**代码**：`src/fin_data_platform/storage/`（schema 生成、写入与读取、读模型、迁移、
只读角色授权 `grants.py`）

## 5. Runtime（控制面）✅

**定位**：常驻控制面进程——"按正确的时间、正确的顺序、可追溯地运行任务"。

**职责**

- **调度**：按数据域与窗口生成任务，交易日历感知，启动即追平历史缺口；
- **分发与执行**：任务按依赖门控入队，工作池并发执行，背压保护；
- **状态与追溯**：任务定义、依赖、运行记录、水位持久化，可查询；
- **健康检查**：启动时校验字典与 schema，配置错误快速失败。

**边界**：编排与状态管理，不含业务口径；派生逻辑属派生引擎；消费出口属消费层。

**关键概念**：角色可拆（单机 / 调度 / 执行，仅凭数据库协调）；幂等键；
水位单调推进；失败重试与断点补数。

**代码**：`src/fin_data_platform/runtime/`（入口、角色、任务仓储、日历、窗口、触发、健康）
与 `src/fin_data_platform/ingestion/`（采集写入与配置装配）

## 6. Derived Engine（派生引擎）🚧

**定位**：派生指标（即因子）的可复现、可审计计算与登记——平台的**因子库**形态。

**职责**

- 算法以代码实现并登记（带版本的稳定标识；升级新增标识、旧实现永久保留）；
- 输入一律来自**访问面**的规范化数据（复权等口径已组合，不用原始 OHLCV）；
- as-of 输入防前视；批量重算；
- 物化：因子全序列的单份投影（可重建、代次切换）；读取严格对齐、不对齐报错；
- 升级与重述台账：记录生效日与原因。

**边界**：列级口径（复权、单位、跨源对齐）归**访问面**，不属于派生；
不存派生结果的多版本；不做因子挖掘与策略研究（属消费侧）。

## 7. Access（访问面）🚧

**定位**：Canonical 与消费方之间的**统一读取层**——把"存起来的原始数据"组合成"可直接计算的数据"。

**职责（规划）**

- **Raw 读取**：PIT（`as_of` / 版本）+ **口径组合**（复权、单位、跨源优先级），
  缺省口径由数据字典声明（行情默认**后复权**——因子/研究口径，历史值不随新除权事件漂移；
  前复权可显式请求，用于与现价对比；指数类无复权）；
- **Factor 读取**：因子（派生指标）读取——物化投影严格对齐知识锚，
  `materialize: none` 的因子按需计算；不对齐报结构化异常，不做 lazy 回填；
  `materialize: latest` 在首次物化前无投影可读（物化是控制面意图，需显式触发）；
  复权口径下缺复权因子的行（NULL）不参与计算；
- **单一实现**：派生计算与消费出口共用同一实现，复权逻辑不出现第二份；
- **读不写库**；回填 / 物化是控制面意图（Runtime 执行，可审计）。

**边界**：只读；不改变数据语义；不是对外契约层（对外契约见 Read Model 与 SDK 文档）。

## 8. Read Model 与消费层 🚧

**定位**：对外只读出口；消费适配器不承载平台语义。

**形态**

- **Read Model**：`mart` 下语义版本化的视图 / 表函数，as-of 语义原生（默认消费入口）；
- **SDK**：三个读面（Raw / Factor / Read Model）+ 控制面意图面；
  直连模式（direct mode）无需经过服务；契约见 [SDK 文档](sdk.md)；
- **REST**：SDK 的薄封装（供管理台与跨语言消费）；
- **批量导出**：研究通道（Parquet / CSV / DuckDB）；
- **管理 API / WebUI**：平台治理界面（数据集字典、实体注册表、任务与水位、同步触发）——
  FastAPI + SPA，同镜像 `service`，默认仅本机。

**边界**：只读；不改变数据语义；权限按数据集裁剪。
