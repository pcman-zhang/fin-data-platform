# 系统理念

> 本文回答一个问题：**我们为什么这样设计**。
> 如果你只想快速上手，请从 [README](../README.md) 出发；想了解结构，读 [系统架构](architecture.md)。

## 1. 问题：金融数据难在哪

金融数据的难，不在于"把数据抓下来"，而在于抓下来之后的三件事：

1. **时间**：一条 2020 年的财务数据，可能是 2021 年才公告的，2022 年被重述的。
   如果不记录"当时的市场知道什么"，任何回测都会前视（look-ahead），任何结论都不可信。
2. **身份**：同一家公司在不同数据源里有不同的代码，代码会变更、会复用；
   股票会上市、停牌、退市。如果身份是随手拼接的字符串，跨源合并终将崩溃。
3. **口径**：不同源的字段含义、单位、复权方式、币种各不相同。
   横向拼接原始字段得到的是"看起来能用"的数据，而不是可以下结论的数据。

大多数数据脚本解决的是"抓取"，这三个问题被留给了使用者。本项目的全部设计，
都是为了在**平台层面**一次性解决它们。

## 2. 一条数据的一生

```
源端响应 ──归一化──▶ Canonical（契约字段 + 时间语义）──▶ Read Model（语义版本出口）
   │                       │                                    │
   │                       └── 派生（算法 + as-of 输入）──────────┘
   └── 原始留存（审计 / 重放 / 对账）
```

- 采集时，平台只信任**显式声明的数据源**，主源失败才按策略回退；
- 落地时，字段、类型、单位、时间角色全部来自**数据字典**，供应商特有字段不进入公共 schema；
- 消费时，使用者只看**语义版本化**的读模型，换源、重洗、重述都不改变出口。

## 3. 六条信条

### 3.1 时间是一等公民

每条数据携带四个时间：**事件时间**（何时发生）、**发布时间**（何时公告）、
**知识时间**（何时可被市场知晓）、**入库时间**（何时进入本平台）。

- `as-of` 查询 = "知识时间 ≤ as_of，按业务键取当时的最新版本"，Canonical 层不落
  `is_latest` 这类会随刷新而变的列；
- **重述不改历史**：修正与重述以新版本追加，旧版本永久保留；
- 复现优先：同一次查询，今天跑与一年后跑，得到同一份数据。

### 3.2 契约先于实现（Schema First）

数据字典是唯一契约：字段名、类型、单位、PIT 角色、主键、质量规则、血缘、源映射，
全部机器可读。

- 数据库 DDL、迁移基线、读模型、生成式文档**由契约派生或强校验**；
- **字段兼容 ≠ 语义兼容**：新增字段不升版本；字段含义、口径、单位变化必须升语义主版本；
- 契约变更走评审与 CI，而不是"先改表再说"。

### 3.3 身份与状态分离

实体注册表（Entity Registry）回答"数据说的是谁"：实体身份、代码履历、关系、外部标识。

- 身份是稳定的、不随交易状态变化的；**交易状态（上市 / 停牌 / 退市）是数据**，
  由数据集承载；
- **公司不等于证券**：同一发行主体可以拥有多只上市证券，财务与行情因此分属
  发行主体（issuer）与上市实体（listing）两侧，由关系连接；
- PIT 宇宙（某个历史时点"应该有哪些标的"）由数据集**推导**，而不是在注册表里维护；
- 关系是词表驱动的：新增关系类型必须先登记，查询、校验、文档都由词表生成。

### 3.4 缓存非权威

缓存（进程内与将来的共享层）永远不是数据源：

- 清空缓存，数据可以完全从权威层重建；
- **禁止任何只存在于缓存的业务状态**；
- 缓存故障时降级放行（fail-open），不阻塞数据链路。

### 3.5 算法即证据

派生数据不存"多份结果"，存**输入与算法**：

- 算法以代码实现，带结构化注释（口径、PIT 规则），并注册为带版本的稳定标识；
- 算法升级 = 新增标识，旧实现永久保留，任何历史数值可回溯到当时的算法版本与输入版本；
- 因子之间**互相依赖**（如 ADX 依赖动向指标、波动率因子依赖收益序列），依赖关系随算法一同
  登记：它决定执行顺序、as-of 语义能否成立、以及一次升级需要重算多少——没有依赖图的因子库，
  只是一堆互不知情的脚本；
- 派生的输出最多保留"最新一份"可重建投影——代码便宜，数据副本昂贵。

### 3.6 源可替换，出口稳定

接入层（FinDataHub）是唯一的数据源访问面，处理适配、归一、限流、缓存与跨源路由；
平台层禁止直连数据源。

- 换源（甚至换供应商）只影响接入层，消费侧无感；
- 消费层（SDK / REST / 导出）只读语义版本化的读模型，不碰 Raw 与 Canonical 物理表；
- 付费源按次计费：合并调用、缓存、按需补充是默认行为，而不是优化项。

## 4. 成本与边界意识

- **成本**：付费数据源"调用次数即成本"。接入层默认合并请求、缓存结果、
  仅在缺数据时补充来源；
- **边界**：本平台只负责"正确的数据、正确的时间语义、正确的身份语义、正确的派生语义"。
  因子挖掘、回测、执行与交易网关属于消费侧，永不在平台内实现。

## 5. 设计后果

这些信条的直接后果是：

- 平台的主体是**库 + 数据库**，而不是一个应用后端；API 只是出口；
- 控制面（调度、质量、血缘、配额）与数据面（契约、存储、派生）分离，
  两者可同机部署，也可拆进程；
- 对外开放的永远是可以自证的数据：每个数值都能回答"从哪来、何时可知、用什么算法算的"。
