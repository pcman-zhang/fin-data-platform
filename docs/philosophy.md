# 系统理念：为什么这样设计

> 本文写给**金融系统开发者**：你在构建研究、回测、监控或下游数据系统，
> 需要一个可信的数据底座。本文解释平台每条设计决策背后的问题与取舍，
> 读完你应该能回答：这个平台保证什么、不保证什么、为什么。
>
> 想直接动手，读 [快速开始](getting-started.md)；想了解结构，读 [系统架构](architecture.md)。

## 1. 金融数据开发的五类失败

把数据抓下来从来不是难点。难的是抓下来之后，数据仍然"不可信"。
下面五类失败在自建数据管道的团队里反复出现，本平台的全部设计都是为了
在平台层面一次性消除它们。

### 1.1 前视偏差（look-ahead）

一条 2020 年 Q1 的财务数据，可能直到 2021 年才公告，2022 年又被重述。
如果数据库里只有"事件时间"（报告期），回测在 2020 年就能读到它——
策略在现实中不可能获得的信息，回测收益率再漂亮也没有意义。
**没有知识时间的数据，只能用于展示，不能用于回测。**

### 1.2 身份漂移

同一家公司在不同数据源里有不同的代码；代码会变更（更名、市场迁移）、
会被复用（退市后代码交给新标的）。用代码字符串做跨源主键，第一次更名
就断链；用名称匹配，第一次改名就错配。**身份必须与代码解耦，且保留履历。**

### 1.3 口径漂移

同一字段在不同源含义不同：成交量有的含大宗有的不含，复权有的前复权
有的后复权，币种、单位、枚举各不相同。把两个源的 `close` 拼在一张表里，
得到的是"看起来能用"的数据，而不是可以下结论的数据。
**口径必须在契约里显式声明，并在读取时统一组合。**

### 1.4 复现失败

同一次查询，今天跑与一年后跑结果不同：上游改了数据、算法升级了版本、
代码路径变了。研究结论无法复核，因子衰减无法归因。
**派生数据必须可回溯到"当时的输入与当时的算法"。**

### 1.5 成本失控

付费数据源按调用计费。自建管道里，"每次请求都实拉"是默认行为，
成本随使用量线性膨胀；限流与预算写在单个进程里，多进程部署后总量失控。
**调用次数是成本，合并、缓存、预算与跨进程配额必须是平台的默认行为。**

## 2. 一条数据的一生

```
源端响应 ──归一化──▶ Canonical（契约字段 + 时间语义）──▶ Read Model（语义版本出口）
   │                       │                                    │
   │                       └── 派生（算法 + as-of 输入）──────────┘
   └── 原始留存（审计 / 重放 / 对账）
```

- **采集时**：平台只信任显式声明的数据源（`source` 参数语义不可变），
  主源失败才按策略回退；每次调用计入限流与预算。
- **落地时**：字段、类型、单位、时间角色全部来自**数据字典**；
  供应商特有字段不进入公共 schema；重述以新版本追加，旧版本永久保留。
- **消费时**：使用者只读**语义版本化**的读模型；换源、重洗、重述都不改变出口。

## 3. 六条信条

### 3.1 时间是一等公民

**决策**：每条数据携带四个时间——**事件时间**（何时发生）、**发布时间**（何时公告）、
**知识时间**（何时可被市场知晓）、**入库时间**（何时进入本平台）。
查询以知识时间为主轴。

**机制**：

- `as_of` 查询 = "知识时间 ≤ as_of，按业务键取当时的最新版本"；
- 修正与重述**追加新版本**，不覆盖历史；
- Canonical 层不落 `is_latest` 这类随刷新而变的列（它是视图状态，不是事实）。

**开发者视角的后果**：回测时传 `as_of=回测日`，拿到的就是当时市场可知的数据；
同一次查询今天与一年后结果一致（复现性）。代价是写入与存储略复杂——
版本键（业务键 + 知识时间 + 版本）取代了简单的 upsert。

### 3.2 契约先于实现（Schema First）

**决策**：数据字典是唯一契约：字段名、类型、单位、PIT 角色、主键、质量规则、
血缘、源映射，全部机器可读。

**机制**：

- 数据库 DDL、迁移基线、读模型、生成式文档**由契约派生或强校验**；
- 契约变更走 CI 校验与评审，而不是"先改表再说"；
- **字段兼容 ≠ 语义兼容**：新增字段不升版本；字段含义、口径、单位变化必须升语义主版本。

**开发者视角的后果**：想知道"有哪些数据、字段什么含义、能否为空"，
读字典（`GET /v1/datasets` 或代码里的声明），不用猜、不用翻供应商文档；
升级平台时，schema 兼容性可校验（SDK 带 schema 版本检查）。

### 3.3 身份与状态分离

**决策**：实体注册表（Entity Registry）回答"数据说的是谁"：实体身份、代码履历、
关系、外部标识。交易状态（上市 / 停牌 / 退市）是**数据**，由数据集承载。

**机制**：

- 实体拥有稳定主键，不随代码变化；代码变更与复用写入履历；
- **公司不等于证券**：财务、股东、公司事件挂发行主体（issuer）；
  行情、复权、成分挂上市实体（listing），由关系连接；
- 某历史时点的可交易集合（PIT 宇宙）由数据集**推导**，不在注册表里维护；
- 关系是词表驱动的：新增关系类型先登记，查询与校验由词表生成。

**开发者视角的后果**：跨源合并先落到统一实体，再做数据 join；
查询历史时点的"应该有哪些标的"用 `GET /v1/entities/universe?as_of=`，
而不是自己拼代码表。

### 3.4 缓存非权威

**决策**：缓存（进程内 L1 + Redis L2）永远不是数据源。

**机制**：

- 清空缓存后，数据可以完全从权威层（数据库 / 源端）重建；
- **禁止任何只存在于缓存的业务状态**（分布式锁等协调原语除外，且不视为数据）；
- 缓存故障时降级放行（fail-open），不阻塞数据链路；恢复后自动接管；
- 键携带 PIT 维度与域代际，同步完成按域失效；跨进程 single-flight 防击穿。

**开发者视角的后果**：缓存问题永远不是数据正确性问题；限流与预算计数
是"可重建的运行时状态"，丢失只影响观测，不影响数据。

### 3.5 算法即证据

**决策**：派生数据不存"多份结果"，存**输入与算法**。

**机制**：

- 算法以代码实现，带结构化注释（口径、PIT 规则），注册为带版本的稳定标识；
- 算法升级 = 新增标识，旧实现永久保留；任何历史数值可回溯到当时的算法版本与输入版本；
- 因子之间可以互相依赖（如 ADX 依赖动向指标），依赖关系随算法登记——
  它决定执行顺序、as-of 语义能否成立、一次升级需要重算多少；
- 派生的输出最多保留"最新一份"可重建投影——代码便宜，数据副本昂贵。

**开发者视角的后果**：读因子时可 pin 已注册的算法标识（不同版本以不同标识注册）；
升级算法不会静默改变历史序列；物化投影带知识锚，读取早于锚点会显式报错，
而不是返回不一致结果。

### 3.6 源可替换，出口稳定

**决策**：接入层（FinDataHub）是唯一的数据源访问面，处理适配、归一、限流、
缓存与跨源路由；平台层禁止直连数据源。

**机制**：

- 换源（甚至换供应商）只影响接入层，消费侧无感；
- 消费层（SDK / REST / 导出）只读语义版本化的读模型；Canonical 数据必须经
  访问面（Access）读取，不得直读物理表；
- 付费源按次计费：合并调用、缓存、按需补充是默认行为。

**开发者视角的后果**：切换数据源不需要改下游代码；读模型语义版本化
（`_v1` / `_v2`）保证字段含义变化时新旧并存过渡，而不是静默破坏。

## 4. 成本与边界意识

- **成本**：调用次数即成本。接入层合并请求、缓存结果、仅在缺数据时补充来源；
  跨进程限流与预算聚合（共享计数）防止多进程超配。
- **边界**：本平台只负责"正确的数据、正确的时间语义、正确的身份语义、
  正确的派生语义"。**因子挖掘、回测、执行与交易网关属于消费侧，永不在平台内实现。**

## 5. 设计后果

这些信条的直接后果：

- 平台的主体是**库 + 数据库**，而不是一个应用后端；API 只是出口；
- **控制面**（调度、质量、血缘、配额）与**数据面**（契约、存储、派生）分离，
  两者可同机部署，也可拆进程水平扩展；
- 对外开放的永远是可以自证的数据：每个数值都能回答"从哪来、何时可知、
  用什么算法算的"。
